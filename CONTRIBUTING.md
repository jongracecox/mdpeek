# Contributing

## Getting Started

```sh
git clone https://github.com/jongracecox/mdpeek.git
cd mdpeek
uv sync
prek install        # or: pre-commit install
```

## Running Locally

```sh
uv run mdpeek --version
uv run mdpeek path/to/doc.md
```

## Installing Globally

After making changes, reinstall to test the global `mdpeek` command:

```sh
uv tool install --force --reinstall .
```

Both `--force` and `--reinstall` are required: `--force` alone reuses cached
wheel builds and won't pick up code changes.

## Project Layout

```
src/mdpeek/
├── __init__.py   # Public API and version
├── __main__.py   # python -m mdpeek
├── cache.py         # memory / disk caches for fetched URLs
├── cli.py           # argparse entry point
├── engines.py       # SQL over tables: sqlite, optional duckdb
├── formats.py       # md / csv / tsv / json / jsonl output
├── model.py         # Section / Document tree and ID lookup
├── options.py       # StrEnum API options and coerce()
├── parse.py         # markdown -> section tree and tables (markdown-it)
├── render.py        # view / structure / full output
├── source.py        # load from path, URL (fetch + cache) or stdin
├── table_output.py  # --table / --tables selection and formatting
└── tables.py        # table extraction, typing, summaries
tests/
├── features/           # Gherkin specs of CLI behaviour
├── step_defs/          # shared pytest-bdd steps for the features
├── fixtures/small/     # one edge case per file (bytes kept exact, see .gitattributes)
├── test_parse.py       # expected trees per fixture
├── test_render.py      # render API
└── test_invariants.py  # structural invariants across all fixtures
```

See [CLAUDE.md](CLAUDE.md) for architecture and conventions.

## Testing

```sh
uv run pytest                  # Quick run on the active Python version
uv run nox                     # Full matrix: Python 3.11, 3.12, 3.13, 3.14
uv run nox -s tests-3.14       # One Python version
uv run nox -s tests_duckdb     # With the optional duckdb engine installed
uv run nox -s eval             # Efficiency eval against the baseline
```

Tests never touch your real cache: an autouse fixture points
`MDPEEK_CACHE_DIR` at a temporary directory, and URL tests use a local HTTP
server fixture (`http_server`), never the network.

DuckDB tests skip when the extra isn't installed; `tests_duckdb` (and the
`test (duckdb)` CI job) runs them.

`noxfile.py` is the source of truth for the test matrix. To add a Python
version, append it to `PYTHON_VERSIONS`, add the classifier in
`pyproject.toml`, and extend the CI matrix in `.github/workflows/tests.yml`.

The coverage badge is generated by only one CI job (the 3.13 job) to avoid
concurrent pushes to the `badges` branch. If you drop or rename that version,
update the `matrix.python-version == '3.13'` conditions in
`.github/workflows/tests.yml`.

### Large fixture and efficiency eval

`tests/fixtures/large/handbook.md` is a ~4,000-line synthetic document,
generated by `scripts/gen_handbook.py` from a skeleton and seeded filler. It
covers every edge case mdpeek handles and plants facts the eval asks about.
The generated file is committed; tests fail if it drifts from the generator.

```sh
uv run python scripts/gen_handbook.py            # regenerate after editing the generator
uv run python scripts/eval.py                    # print and write evals/report.md
uv run python scripts/eval.py --update-baseline  # accept new numbers (review the diff!)
uv run nox -s eval                               # what CI runs: freshness + --check
```

`evals/scenarios.toml` lists questions, the mdpeek calls an agent would make,
and the text the answer must contain. CI fails if an answer goes missing or a
scenario costs more than 10% above `evals/baseline.json`. If a change makes
output legitimately larger, update the baseline in the same PR and say why.

### Behaviour specs (BDD)

CLI behaviour is specified in `tests/features/*.feature` (Gherkin) and run by
pytest-bdd through the shared steps in `tests/step_defs/test_cli_steps.py`.
These files are the contract for any future reimplementation (such as a Rust
CLI), so:

- describe what a user runs and sees, not Python internals;
- reuse the existing steps (`Given a markdown file containing:`,
  `When I run "mdpeek …"`, `Then the output is:`, `Then stderr contains:`,
  `Then the exit code is N`) and add new ones sparingly, in the same
  language-neutral style;
- add a scenario for every user-visible behaviour change.

Unit tests (`tests/test_*.py`) cover internals: parsing, the API and edge
cases.

## Code Style

Pre-commit hooks (run by prek) enforce:

- **ruff** for linting and auto-formatting
- **ty** for type checking
- YAML/TOML validity, trailing whitespace, end-of-file newlines
- no direct commits to `main`

Hooks run automatically on `git commit`. If a hook auto-fixes files, re-stage
and commit again. CI runs the same hooks on every pull request.

## Commits and Pull Requests

Commit messages follow [Conventional Commits](https://www.conventionalcommits.org/):

```
<type>(<optional scope>): <imperative summary>

<optional body>

<optional footers>
```

- **Types:** `feat`, `fix`, `docs`, `test`, `refactor`, `perf`, `build`,
  `ci`, `chore`.
- **Scope:** the affected module, if useful, e.g. `feat(tables): add --tables
  listing` or `fix(cli): reject unknown section IDs`.
- **Breaking changes:** add `!` after the type/scope (`feat(cli)!: …`) or a
  `BREAKING CHANGE:` footer.

Pull requests are **rebase merged**, so every commit on a branch lands on
`main` unchanged. Keep a branch to a short list of meaningful commits, one per
logical change, and squash fixups into the commit they belong to before
merging.

## Releasing

Releases are published by `.github/workflows/release.yml` when a tag matching
`v*` is pushed.

### Versioning

The package version is derived from git tags by `hatch-vcs`; there is **no**
`version` field in `pyproject.toml`. Tag `v0.1.1` builds package version
`0.1.1`. Untagged commits get a dev version such as `0.1.1.dev3`.

### Cutting a release

```sh
git checkout main
git pull
git tag v0.1.1
git push origin v0.1.1
```

The release workflow then runs:

1. **Build**: sdist and wheel with `uv build`.
2. **Publish to TestPyPI**: waits for manual approval in the `testpypi`
   GitHub environment, then uploads via OIDC trusted publishing.
3. **Publish to PyPI**: waits for a second approval in the `pypi`
   environment, then uploads.
4. **GitHub release**: created from the tag with the built artifacts and
   generated notes.

Approve in **Actions → release run → Review deployments**. Between the two
approvals, sanity-check the upload at https://test.pypi.org/project/mdpeek/.

### Updating the Homebrew formula

The formula in [jongracecox/homebrew-tap](https://github.com/jongracecox/homebrew-tap)
is not updated by the release workflow. Once the release is on PyPI, run the
tap's `bump-pypi-formula` workflow by hand:

```sh
gh workflow run bump-pypi-formula -R jongracecox/homebrew-tap
```

It points `Formula/mdpeek.rb` at the latest PyPI sdist, refreshes its
dependency resources, then builds, tests and audits it on macOS before
committing to the tap. Pass `-f version=X.Y.Z` to pin a version. Check the run
at https://github.com/jongracecox/homebrew-tap/actions.

The formula's `test do` block runs the installed CLI. If a release changes
the behaviour it checks, update that block in the tap before running the
workflow, or the bump will fail.

### Recovering from a bad release

PyPI and TestPyPI versions are immutable: you cannot re-upload `v0.1.1` once
published.

- **Caught at the TestPyPI stage**: reject the PyPI deployment, fix the
  problem, and push a new tag (e.g. `v0.1.2`).
- **Caught after the PyPI publish**: yank the version on pypi.org
  (Manage → Yank), then push a fix tag.

Never delete and re-push a tag.

### One-time setup

- **PyPI and TestPyPI**: a pending trusted publisher for project `mdpeek`,
  owner `jongracecox`, repository `mdpeek`, workflow `release.yml`,
  environment `pypi` / `testpypi` respectively.
- **GitHub environments** `testpypi` and `pypi`, each with a required
  reviewer and deployment limited to `v*` tags.
- **Merge method**: rebase merge only (merge commits and squash merging are
  disabled in the repository settings).
- **Branch ruleset on `main`**: require a pull request and the `pre-commit`
  and `tests` status checks; block force pushes and deletion.
- **Actions workflow permissions** can stay read-only: the job that pushes
  the coverage badge to the `badges` branch requests `contents: write`
  itself.

See PyPA's Trusted Publishing docs: https://docs.pypi.org/trusted-publishers/
